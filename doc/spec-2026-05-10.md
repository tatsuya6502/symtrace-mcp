# symtrace-mcp Design Specification

## 1. Background and Goals

### Current Challenges

| Tool | Approach | Memory | Symbol-level Reverse Dependencies | Rust Trait Resolution |
|------|----------|--------|----------------------------------|----------------------|
| [ast-outline] | tree-sitter (lightweight) | ~100MB | File-level only | No |
| [serena] | LSP (always-on) | ~4GB | Yes | Yes |
| [codegraph] | tree-sitter + SQLite | ~100MB | Yes (approximate) | No |

ast-outline is lightweight and fast, but **symbol-level reverse dependency search** (who calls a given function) and **Rust trait implementation resolution** require an LSP. Serena provides these but consumes ~4GB with rust-analyzer always running.

[ast-outline]: https://github.com/aeroxy/ast-outline
[serena]: https://github.com/oraios/serena
[serena-fork]: https://github.com/tatsuya6502/serena/tree/lazy-language-server
[codegraph]: https://github.com/colbymchenry/codegraph

### Goals

A lightweight tool that handles only LSP-required operations while ast-outline covers most code exploration.

- **Lazy LSP startup** only when needed ([serena-fork]'s deferred launch pattern)
- **Automatic shutdown on idle** (memory reclamation)
- **Native Rust** implementation (single binary distribution; author is proficient in Rust)
- **MCP server** mode (daemon managing LSP lifecycle)

## 2. Design Principles

| Principle | Rationale |
|-----------|-----------|
| Rust implementation | Distributable as a single binary. The author is proficient in Rust |
| Minimal scope | Only features that require LSP. AST parsing and search delegated to ast-outline |
| Lazy startup + auto-shutdown | Avoids Serena's always-on 4GB footprint |
| Language servers defined via config file | Handles user environment differences |
| MCP server as daemon | LSP server start/stop/idle monitoring requires a persistent process |

## 4. LSP Client Layer

### 4.1 Protocol Handling

LSP uses JSON-RPC 2.0 over stdio (with `Content-Length` header).

```rust
// src/lsp/transport.rs
struct LspTransport {
    child: Child,                          // Language server process
    stdin: BufWriter<ChildStdin>,          // Send requests
    stdout: BufReader<ChildStdout>,        // Receive responses
    pending: HashMap<i64, oneshot::Sender<Value>>,  // Pending requests
    next_id: AtomicI64,                    // Request ID counter
}

impl LspTransport {
    async fn send_request(&self, method: &str, params: Value) -> Result<Value>;
    async fn send_notification(&self, method: &str, params: Value) -> Result<()>;
    async fn read_response(&mut self) -> Result<Option<(i64, Value)>>;
}
```

### 4.2 LSP Lifecycle

Each language server follows this lifecycle:

```
[Not started] → initialize → initialized → [Running] → shutdown → exit → [Terminated]
                                              ↑                        │
                                              └─── (lazy restart) ←───┘
```

```rust
// src/lsp/client.rs
struct LspClient {
    transport: LspTransport,
    root_uri: String,
    open_files: HashSet<String>,           // Currently open file URIs
    capabilities: ServerCapabilities,      // Server capabilities (from initialize response)
}

impl LspClient {
    // Lifecycle
    async fn start(config: &LanguageServerConfig, root: &Path) -> Result<Self>;
    async fn shutdown(&mut self) -> Result<()>;

    // File management
    async fn did_open(&mut self, uri: &str, text: &str, version: i32) -> Result<()>;
    async fn did_close(&mut self, uri: &str) -> Result<()>;
    async fn did_change(&mut self, uri: &str, text: &str, version: i32) -> Result<()>;

    // Queries (core features)
    async fn goto_definition(&self, uri: &str, position: Position) -> Result<Vec<Location>>;
    async fn references(&self, uri: &str, position: Position) -> Result<Vec<Location>>;
    async fn implementations(&self, uri: &str, position: Position) -> Result<Vec<Location>>;
    async fn hover(&self, uri: &str, position: Position) -> Result<Option<Hover>>;
    async fn diagnostics(&self, uri: &str) -> Result<Vec<Diagnostic>>;
    async fn rename(&self, uri: &str, position: Position, new_name: &str) -> Result<WorkspaceEdit>;
    async fn incoming_calls(&self, uri: &str, position: Position) -> Result<Vec<CallHierarchyItem>>;
    async fn outgoing_calls(&self, uri: &str, position: Position) -> Result<Vec<CallHierarchyItem>>;
}
```

### 4.3 File Management

`textDocument/didOpen` must be sent before LSP queries. File contents are read from disk each time.

```rust
// src/lsp/file_manager.rs
struct FileManager {
    open_files: HashMap<String, OpenFile>,  // URI → metadata
}

struct OpenFile {
    version: i32,
    modified_at: std::time::SystemTime,    // File mtime
}

impl FileManager {
    /// Open a file (send didChange if already open and content has changed)
    async fn ensure_open(&mut self, client: &mut LspClient, path: &Path) -> Result<()>;
    /// Close a file
    async fn close(&mut self, client: &mut LspClient, path: &Path) -> Result<()>;
}
```

## 5. Language Server Management

### 5.1 Lazy Startup

Language servers start on the first tool call. The tool call waits until startup completes.

```rust
// src/server/manager.rs
struct LanguageServerManager {
    configs: HashMap<Language, LanguageServerConfig>,
    clients: Mutex<HashMap<Language, LspClient>>,       // Active clients
    file_managers: Mutex<HashMap<Language, FileManager>>,
    idle_monitor: IdleMonitor,
    root: PathBuf,
}

impl LanguageServerManager {
    /// Get the language server for a file path (start if needed)
    async fn get_client_for_file(&self, path: &Path) -> Result<(Language, MutexGuard<LspClient>)>;

    /// Start a language server
    async fn start_server(&self, language: Language) -> Result<()>;

    /// Stop a language server
    async fn stop_server(&self, language: Language) -> Result<()>;
}
```

### 5.2 Automatic Shutdown (IdleMonitor)

Automatically stops language servers that have had no tool access for the configured duration.

```rust
// src/server/idle_monitor.rs
struct IdleMonitor {
    last_used: Mutex<HashMap<Language, Instant>>,
    timeout: Duration,                    // Default: 300 seconds (5 minutes)
    check_interval: Duration,             // Default: 60 seconds
    running: AtomicBool,
}

impl IdleMonitor {
    /// Update access time (called on every tool invocation)
    fn touch(&self, language: Language);

    /// Periodic check in the background
    async fn run(&self, manager: &LanguageServerManager);
}
```

### 5.3 Supported Languages

Initial implementation supports the following 3 languages. Additional languages can be added via configuration.

| Language | Server | Notes |
|----------|--------|-------|
| Rust | `rust-analyzer` | Trait implementation resolution is the primary use case |
| TypeScript / TSX | `typescript-language-server` | Needed for React development |
| Python | `pyright` | Same choice as Serena |

```rust
// src/server/config.rs

}
```

## 6. MCP Server

### 6.1 Why an MCP Server?

symtrace-mcp needs a **persistent process** to manage LSP server start/stop/idle monitoring. Implementing as an MCP server provides:

- Claude Code starts and manages the process (just register in `.claude/settings.json`)
- The MCP server process stays resident, managing LSP server lifecycle
- IdleMonitor runs on a background thread
- No overhead of restarting the process on each tool call

ast-outline is stateless (full scan each time) so an MCP server is optional, but symtrace-mcp is stateful (maintains LSP connections) so an MCP server is required.

### 6.2 Protocol

JSON-RPC 2.0 over stdio. Uses tokio runtime (LSP client is async).

### 6.3 Provided Tools

Curated to operations that are **impossible** with ast-outline and **require** an LSP.

| Tool Name | LSP Method | Description | Priority |
|-----------|------------|-------------|----------|
| `find_references` | `textDocument/references` | Full symbol-level reference search. ast-outline's `reverse-deps` is file-level; this is symbol-level | ★★★ |
| `goto_definition` | `textDocument/definition` | Jump to definition. ast-outline uses name matching; LSP uses resolved types | ★★★ |
| `find_implementations` | `textDocument/implementation` | Find trait/impl/interface implementations. Especially important for Rust | ★★★ |
| `incoming_calls` | `callHierarchy/incomingCalls` | Callers (who calls this function) | ★★★ |
| `outgoing_calls` | `callHierarchy/outgoingCalls` | Callees (what this function calls) | ★★☆ |
| `hover` | `textDocument/hover` | Display type information and documentation | ★★☆ |
| `diagnostics` | `textDocument/diagnostic` | Get errors and warnings | ★☆☆ |
| `rename` | `textDocument/rename` | Workspace-wide rename | ★☆☆ |

### 6.4 Tool Schema Examples

```
find_references:
  parameters:
    - file_path: string (required) — Absolute path to the target file
    - line: integer (required) — Line number (1-based)
    - column: integer (required) — Column number (1-based)
  returns:
    - locations: [{ file_path, line, column, line_text, context }] — List of reference locations
```

```
incoming_calls:
  parameters:
    - file_path: string (required)
    - line: integer (required)
    - column: integer (required)
    - depth: integer (default: 1) — Call chain depth
  returns:
    - callers: [{ name, file_path, line, column, callers: [...] }]
```

### 6.5 Output Format

Human-readable (AI agent-friendly) text format by default, with `json: true` parameter for structured output.

```
find_references: my_function
  src/foo.rs:42:5  fn my_function(x: i32) -> bool {
  src/bar.rs:128:10    let result = my_function(42);
  src/baz.rs:55:3      my_function(data.value);
  (3 references in 3 files)
```

```
incoming_calls: my_function (depth=1)
  ← src/bar.rs:128:10  process_data()
  ← src/baz.rs:55:3    handle_request()
  (2 callers)
```

## 7. Configuration

### 7.1 Project Configuration File

Place `.symtrace.toml` in the project root.

```toml
# .symtrace.toml

# Common settings
idle_timeout_secs = 300       # Seconds before idle auto-shutdown

# Language server definitions
[[language_servers]]
language = "rust"
command = "rust-analyzer"
extensions = ["rs"]

[[language_servers]]
language = "typescript"

args = ["--stdio"]
extensions = ["ts", "tsx", "js", "jsx"]
idle_timeout_secs = 300

[[language_servers]]

command = "pyright-langserver"
args = ["--stdio"]
extensions = ["py"]
idle_timeout_secs = 300
```

`~/.symtrace.toml` can set common defaults. Project configuration takes precedence.

## 8. Integration with ast-outline

### 8.1 Role Division

```
Code exploration flow:

1. Structure overview      → ast-outline outline / digest
2. Symbol body inspection  → ast-outline show
3. Implementation search   → ast-outline implements
4. File dependencies       → ast-outline deps / reverse-deps
5. Public API surface      → ast-outline surface
6. Search                  → ast-outline search / find-related
7. ↑ Above: ast-outline (fast, lightweight, stateless)

8. Symbol reference search  → symtrace-mcp find_references    ← NEW (LSP)
9. Trait implementation     → symtrace-mcp find_implementations ← NEW (LSP)
10. Call hierarchy          → symtrace-mcp incoming_calls       ← NEW (LSP)
11. Type information        → symtrace-mcp hover                ← NEW (LSP)
12. Jump to definition      → symtrace-mcp goto_definition      ← NEW (LSP)
```

### 8.2 Integration Approach Differences

ast-outline and symtrace-mcp use different integration approaches.

**ast-outline** — CLAUDE.md prompt injection:
- `ast-outline install --target claude-code` injects a prompt snippet into CLAUDE.md
- Claude Code runs ast-outline as a CLI command (via Bash tool)
- Stateless: independent process starts each time, state discarded on exit
- Also has an MCP server mode, but not required

**symtrace-mcp** — MCP server:
- Register as MCP server in `.claude/settings.json`
- Claude Code starts the symtrace-mcp process and keeps it running
- Stateful: maintains LSP server connections and continuous idle monitoring
- MCP server is required (no persistent process = no LSP lifecycle management)

### 8.3 Claude Code Configuration

```json
// .claude/settings.json
{
  "mcpServers": {
    "symtrace-mcp": {
      "command": "symtrace-mcp",
      "args": ["mcp"]
    }
  }
}
```

ast-outline is already integrated via `ast-outline install --all` into CLAUDE.md.

### 8.4 Proposed CLAUDE.md Guidelines

Append the following usage guide after the ast-outline prompt snippet:

```markdown
## symtrace-mcp — LSP-based Symbol Analysis

Use symtrace-mcp when you need LSP features that ast-outline cannot provide (symbol-level reference search, trait resolution, etc.).

When to use which:
- **Structure and signature inspection**: Use ast-outline (fast, lightweight)
- **Reference search and caller search**: Use symtrace-mcp's find_references / incoming_calls
- **Rust trait implementation resolution**: Use symtrace-mcp's find_implementations
- **Jump to definition**: Use symtrace-mcp's goto_definition
- **Type information**: Use symtrace-mcp's hover

symtrace-mcp is provided as MCP tools. The first invocation starts the LSP server, so there may be a slight delay.
```

## 9. Implementation Plan

### 9.1 Phases

| Phase | Content |
|-------|---------|
| **P0: Foundation** | LSP transport, protocol types, MCP server framework |
| **P1: Minimal Features** | rust-analyzer only. `find_references`, `goto_definition`, `find_implementations` |
| **P2: Call Hierarchy** | `incoming_calls`, `outgoing_calls` (callHierarchy protocol) |
| **P3: Multi-language** | TypeScript, Python support. Configuration file introduction |
| **P4: Advanced Features** | `hover`, `diagnostics`, `rename` |

## 11. Decisions

### 11.1 LSP Index Wait Strategy

Use a **combination of B + C**. First, poll with `textDocument/documentSymbol` until a non-empty result is returned (C); if that fails, retry with a timeout (B).

### 11.2 Multi-project Support

Start with single-project support. Multi-project support will be considered in the future.

### 11.3 `callHierarchy` Protocol Support Status

Python (pyright) does not support `callHierarchy`. Use `find_references` as a fallback. Python is low priority, so this will be handled in P3.

### 11.4 No Serena Coexistence

symtrace-mcp replaces Serena entirely. The goal is ast-outline + symtrace-mcp with no Serena dependency.
